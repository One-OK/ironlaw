# 变更纪律（精简版）

> 完整方法论见 WorkBuddy 技能 `ironlaw-change`。本文件是仓库内的**可执行摘要**。
> 核心：任何改动都走五段，不许"这次小改动例外"。

## 四条铁律

| # | 铁律 | 判据 |
|---|---|---|
| 一 | 必填必须 fail-closed | 喂空数据（空数组/缺章节/缺文件/超时）跑一次，放行 = 规范不存在 |
| 二 | 新守卫必须带反向探针 | 去掉保护必须转红，快照还原法验证可逐字节复原 |
| 三 | 跨脚本口径单一真源 | 判定规则只许一处实现（`scripts/lib/`），两份 = 互相掩护 |
| 四 | 影响链靠机器算的覆盖率 | 机器列范围键，逐键闭环；漏的键点名 |

## 开工六问（答不全不许动手）

1. **缺数据行为**：缺文件/缺章节/缺参数/空数组/超时/异常时判红还是判绿？判绿的写理由。
2. **根因位置**：真源在哪（不是症状出现的地方）？
3. **影响链**：渲染/契约/产物/测试/文档/联动，六类哪些会跟着变？
4. **失败可见性**：改坏了谁先发现？有没有断言能在提交前钉住？
5. **反向变异**：把修复去掉，哪条断言会转红？
6. **裁定归属**：命名/口径/交互语义拿不准的，列选项让用户拍板。

## 五段流程

### 第〇段 · 验证设施免责先行

**任何 FAIL，先证明验证设施本身没病，再改代码。**

1. 单独重跑：单跑过、批量不过 ⇒ 设施污染，不是产品回归
2. 时间线取证：`git log` 区间有无相关改动？零相关 ⇒ 数据漂移或抖动
3. 前一条是 soft 超时 ⇒ 先重跑再下结论

### 第 1 段 · 动手前

根因一句话写出来（"根因是 X，不是 Y"）；影响链列表；裁定问用户。

### 第 2 段 · 修复中

改真源不改显示点；全链一次做完；测试与契约同批更新。

### 第 3 段 · 上线前复检

1. 残留 grep 为 0
2. 专项扫描重跑
3. 全量门禁绿（日志末尾有 `EXIT=0` 哨兵）
4. 用户路径冒烟（只读 ≠ 交互，写路径必须真点一遍）

### 第 4 段 · 固化

一次性检查 → 常驻守卫（`scripts/check-*.mjs` + 注册进聚合器）。
变更档案七段 + §2.5 机器断言（见 `docs/change-records/`）。

## 复盘三问

1. 哪个**机制**没做？（不是"我不够仔细"）
2. 为什么没做？（不知道 / 来不及 / **机制允许**）
3. 机制改了什么，让它下次**不可能**被跳过？

> 第 3 问答成"下次更仔细" = 复盘失败，回到第 1 问。

## 提交信息三段

```
<type>(<scope>): <结果>

根因: <机制层面一句话>
影响链: ① ... ② ... ③ ...
验证: <命令 → 结果>
```

由 `.githooks/pre-push` 机械校验，缺段推不出去。

## 上线

推送 ≠ 上线。真值只认：远端分支指针、线上 `/api/config` 版本、分发通道 manifest。
完整清单见 WorkBuddy 技能 `ironlaw-ship`。
