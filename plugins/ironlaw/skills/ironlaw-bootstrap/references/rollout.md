# 渐进落地路线

## 为什么不能一次铺满

一个 20 分钟跑不完的门禁，人不跑；不跑的门禁等于不存在。而一个只有 3 条规则的骨架，人会跑，跑久了还会主动加。

**可维护性 > 完备性。** 完备性靠时间堆，不靠第一天抄。

---

## 四阶段

### 阶段 1 · 建仓当天（13 个文件）

装脚手架，拿到四组验收输出。

此时的保护：

- 编码/乱码
- JSON BOM
- 提交信息三段
- 未注册的门禁脚本（防止自己写了自己不跑）
- 敏感文件与构建产物不进库

没有：类型检查、测试、契约。**这是对的**——项目还没有代码。

### 阶段 2 · 第一周：把已有的检查接进来

有了第一个能跑的命令，就把它加进 `check-all.mjs` 的 `STEPS`：

```js
{ name: '类型检查', cmd: 'npx tsc --noEmit --incremental false', timeoutMs: 300_000 },
{ name: '单元测试', cmd: 'npm test -- --runInBand', timeoutMs: 1_800_000 },
{ name: '构建', cmd: 'npm run build', timeoutMs: 600_000 },
```

注意：

- **超时预算要给足**（历史耗时的 2~3 倍），否则会变成"随机红"
- 慢步骤（>2 分钟）放在后面，前面的快步骤先失败，省时间
- 每个步骤名写"守什么"，不写脚本名

### 阶段 3 · 第一月：按第一次事故加

事故形态 → 该加的规则：

| 事故 | 加什么 |
|---|---|
| 两端字段名不一致 | 契约检查（前端调用点 vs 后端路由） |
| 用户看到工程话术 | 文案词表扫描 |
| 权限越权 | 作用域合并守卫（`AND` 不得被 `OR` 覆盖） |
| 同一概念两种叫法 | 术语真源 + 同义词零残留 |
| 删了功能但入口还在 | 死代码/死路由扫描 |
| 数据写入没校验归属 | 写路径契约检查 |

每条都用 `guard-skeleton.mjs` 起手，5 分钟内能立。

### 阶段 4 · 长期：每条事故长一条

判据：

> 这次事故，**下次能不能被一条机械规则拦住**？

能 → 加规则。不能（如"架构选错了"）→ 写进决策记录，不要硬造门禁。

## 什么时候**不该**加门禁

| 情况 | 为什么不加 | 改做什么 |
|---|---|---|
| 规则本身还在变（一周改三次） | 门禁会变成维护负担 | 先稳定规则，再固化 |
| 只能靠人判断（"这个命名好不好"） | 无法机械判定 | 写进 review 清单 |
| 触发频率极低（一年一次） | 记忆成本 > 守护收益 | 写进 checklist |
| 加了会误伤大量正常代码 | 会被关闭，比没有更坏 | 缩小判据范围，或改白名单 |

**宁窄勿宽**：宽了会被当"狼来了"关掉，比没有守卫更坏。

## 老项目怎么补

跟新项目不同：老项目已经有一堆不合规的存量。

### 三步

1. **先测基线**：跑一遍规则，把当前命中数记成 baseline（如 `allowed: 137`）
2. **判据改成"只降不升"**：`hits <= baseline`，新代码不许增加
3. **逐步压降**：每次修一批，把 baseline 调低

```js
// scripts/redlines-baseline.json
{ "no-raw-table": 0, "hardcoded-color": 137, "manual-row-actions": 12 }
```

判据：

```
本次命中数 <= baseline 中记录的数  → 通过
本次命中数 <  baseline 中记录的数  → 通过，并提示可以下调 baseline
本次命中数 >  baseline             → 判红，点名新增位置
```

这样存量不会阻塞上线，增量被彻底锁死。

### 顺序

先补**零存量**的规则（编码、BOM、提交信息），立刻生效；
再补**小存量**的；最后才是大存量的（硬编码颜色之类）。

---

## 加到什么程度算够

一个够用的纪律体系，应该满足：

| 判据 | 说明 |
|---|---|
| 全量门禁 < 15 分钟 | 超过就没人愿意在提交前跑 |
| 每次红都能定位到文件 | 红线不可定位 = 会被忽略 |
| 单条规则 < 5 秒 | 慢的单独放，不进快速反馈环 |
| 每条规则都有反向探针 | 没有就等于没有 |
| 规则数量与事故数量正相关 | 一堆没人踩过的规则是负债 |

最后一条最重要：**规则应该长得像你的历史事故，而不是像别人的最佳实践清单。**
