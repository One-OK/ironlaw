# 改动纪律：根因 · 全链 · 复检 · 固化

## 这个技能解决什么

绝大多数"改坏了"不是技术不够，而是**流程缺环**：改了显示点没改真源、修一处漏一串、红了门禁照样推、修完不留守卫所以三个月后同款事故再来一次。

本技能把这条链路做成不可跳过的顺序。**任何一次改动都走这五段，不许"这次小改动例外"。**

## 四条铁律（凌驾于一切具体做法之上）

| # | 铁律 | 一句话判据 |
|---|---|---|
| 一 | **必填必须 fail-closed** | 把机制喂空数据（空数组/缺章节/缺文件/超时）跑一次，放行 = 这条规范不存在 |
| 二 | **新守卫必须带反向探针** | 去掉保护必须转红，且用快照还原法证明可逐字节复原 |
| 三 | **跨脚本口径单一真源** | 判定规则只许一处实现，落在 `scripts/lib/`；两份 = 迟早互相掩护 |
| 四 | **影响链靠机器算的覆盖率** | 机器列出本次触及的范围键，逐键闭环；漏的键点名，不靠人脑枚举 |

详见 `references/iron-laws.md`。**铁律一是最容易自欺的一条**——写文档说"必须"，代码里 `if (!x.length) return OK`，回头读输出全绿，于是以为自己没问题。

## 五段流程

### 第〇段 · 验证设施免责先行

**任何 FAIL / 红 / 报障，在改一行产品代码之前，先证明验证设施本身没病。**
否则会把设施抖动当产品缺陷去修——越修越坏，还把真缺陷挤出注意力。

判别三连，按序做：

1. **单独重跑**：单独跑能过、批量里不过 ⇒ 跨场景状态污染 / 冷启动竞态，不是产品回归。
2. **时间线取证**：PASS→FAIL 两次运行之间 `git log` 有无相关改动？零相关 ⇒ 大概率数据漂移或抖动。
3. **失败前一条是 soft 超时 ⇒ 先重跑再下结论**（冷启动竞态固定前兆）。

⇒ 纪律：**先重跑、再取证、后动手。** 把"批量红、单独绿"当回归去修产品，是最贵的一种错。

### 第 1 段 · 动手前（不写完不准改代码）

**开工六问**，答不全不许动手：

1. **缺数据行为**：这条判据在缺文件/缺章节/缺参数/空数组/超时/异常时判红还是判绿？判绿的每一处能否说清"为什么放行是安全的"？
2. **根因位置**：真源在哪？（不是症状出现的地方）
3. **影响链**：改这个符号，全仓哪些渲染点/契约点/产物点/测试点/文档点/联动点会跟着变？
4. **失败可见性**：改坏了，谁会先发现？多久能发现？有没有断言能钉住？
5. **反向变异**：把修复去掉，哪条断言会转红？说不出 = 这条修复没有被验证。
6. **裁定归属**：命名/口径/交互语义拿不准的，列选项让用户拍板，禁止自以为。

**根因不要停在第一层。** 用户报"列顺序反了"，真源可能是"入口列序与人读顺序相反"，而不是"解析函数写错了"。往上多问一层，往往省掉两轮返工。见 `references/intake.md` 的症状→真源映射表。

**根因还不知道时，走调试程序，不许猜修**：复现 → 最小化 → 假设证伪 → 修复闭环，四段见 `references/debugging-procedure.md`。复现不出来就动手改，是最贵的一种开工方式。

**影响链六类**，逐类 grep 并写清单，改完划掉：

| 类 | 典型位置 |
|---|---|
| 渲染点 | 组件 / 列表列 / 详情配置 / 页签 |
| 契约点 | API 请求响应 / DTO / 控制器 / 共享类型包 |
| 产物点 | PDF / Excel / 导出模板 / 打印样式 |
| 测试点 | 单测断言 / e2e 场景 / 基线快照 |
| 文档点 | 台账 / 设计文档 / 注释里的旧名 |
| 联动点 | watch / 派生逻辑 / 后端 ensure* 同步 / 缓存失效 |

漏一类 = 漏一串。改了字段名没改导出模板 = 客户拿到的单证和系统不一致；测试没跟着改 = 假红或更危险的假绿。

### 第 2 段 · 修复中（根因 + 全链一次做完）

- **改真源，不改显示点**：显示点一律引用真源，禁止在组件里手写与真源同义的副本。
- **全链改完才验证**：禁止"先改主要的，其他以后"——"以后"就是永远。
- **测试与契约同批更新**：测试绿了但断言的是旧语义 = 假绿，比红更危险。
- **写操作必须验证归属与作用域**：改任何"按 id 操作"的接口，先问"这个 id 属于当前用户/租户吗"。

### 第 3 段 · 上线前复检（没有复检 = 没修完）

机械复检四连，缺一不可：

1. **残留 grep**：旧值/旧名/旧模式全仓出现数为 0（白名单须注明理由）。
2. **专项扫描**：把本次问题固化成扫描规则重跑。
3. **全量门禁**：绿，且日志末尾有独立哨兵（见 `ironlaw-gate` 技能）。
4. **用户路径冒烟**：只读检查只证明"不崩"，不等于"路径对"。动了列表/表单/分页 → 必须真交互点一遍：翻页、搜索、提交、回读落库。

**部署后的检查叫"对线上真值说话"，不叫"复检"**——它验的是产物，不是代码。

### 第 4 段 · 固化（修一个，防一片）

- 一次性检查必须变成常驻守卫。**同一个问题不允许被两个人各自重新发现一遍。**
- 守卫写法见 `ironlaw-gate` 技能。
- 变更档案与提交信息见 `ironlaw-record` 技能。

## 测试先行（三种情况：红 → 绿 → 固化）

不是所有改动都要先写测试（测试数量同样与事故正相关，不与仪式感正相关），但以下三种**必须先让测试红**：

| 情况 | 为什么 |
|---|---|
| **修 bug** | 先用失败测试钉住 bug（最小复现 → 测试）再修——否则无法区分「修好了」和「这轮没发作」 |
| **新增会被多处调用的公共逻辑** | 调用方不会都记得验证；行为必须有一处机器可查的契约 |
| **解析 / 序列化 / 权限判定等边界逻辑** | 边界错了伤害最大，且最容易被重构悄悄改掉 |

流程：最小复现（见 `references/debugging-procedure.md` 阶段二）→ 失败测试（红）→ 修复（绿）→ 测试留在套件里。

与 §2.5 断言的分工：**单测钉行为，断言钉残留与规模**——不互相替代。恒真测试（写完没见过它红）不算测试，与「没做过反向探针的守卫」同罪。

> 判据一句话：这个逻辑改坏了，谁会先知道？答案是「没人」→ 先写测试。

## 复盘三问（每次事故必答）

1. 这个缺陷是**哪一环**没做？定位到具体机制，不是"我不够仔细"。
2. 那一环**为什么**没做？不知道 / 来不及 / **机制允许** —— 三者处置完全不同。
3. 机制改了什么，让它下次**不可能**被跳过？

> 第 3 问答成"我下次会更仔细" → **复盘失败**，回到第 1 问。

## 反合理化清单（识别到就驳回自己）

| 借口 | 驳回 |
|---|---|
| "这只是小改动" | 小改动改的是共享真源时，影响面按最坏算 |
| "先跑通再说" | 跑通的是症状，留下的是根因 |
| "测试过了就行" | 测试断言的是旧语义时，绿比红更危险 |
| "门禁是环境问题" | 先拿出单跑通过 + 时间线零相关的证据，再谈环境 |
| "用户没报这个" | 影响链是机器算的，不是用户报的 |
| "以后补守卫" | 以后 = 永远；守卫和修复同一个提交 |

## 多写者并行

只要有第二个人/第二个 Agent/第二条发布线在同一个仓库动，开工前必须对账，合并必须按内容叠加而不是整文件取一边。见 `references/multi-writer-merge.md`。
