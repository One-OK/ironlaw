# 调试程序：从「现象」到「根因」的可复现路径

## 这份文档解决什么

`triage.md` 解决「失败是不是验证设施造成的」（第〇段）；`intake.md` 解决「找到根因后往哪改、真源在哪」。中间缺的一段是：**设施没病、真源未知时，怎么程序化地把根因找出来。**

绝大多数"越修越坏"不是智力不够，是跳过了下面四段中的某一段。按序走，不许跳。

## 阶段一 · 复现（稳定复现优先于一切）

改代码之前，必须有一条**可重复执行**的复现路径。判据：

> 把复现步骤交给一个不了解这个 bug 的人，他能独立碰到同样的现象吗？

- 能 → 进入阶段二
- 时灵时不灵 → 先修**可复现性**，不是修 bug：固定环境（同一分支/同一数据/同一浏览器/同一时区），记录每次尝试的差异（时间、数据量、并发、缓存状态）。随机性本身就是线索——通常指向竞态、缓存或数据状态依赖
- 完全不能复现 → 只做**只读取证**（日志、监控、时间线、报警记录），列出候选假设清单，**不许改产品代码**；清单带着等下一次出现时抓现场

**真实代价**：没有稳定复现就动手修，修完之后你无法区分「修好了」和「这轮它自己没发作」——两种情况你都会宣布成功。

## 阶段二 · 最小化（最小化本身就是二分的开始）

把复现用例砍到最小：最小输入、最短路径、最简环境。

- 每砍一刀现象还在 → 记录「这部分无关」；现象消失 → 你刚砍掉的就是嫌疑区
- 典型刀法：换确定数据 → 关并发 → 关缓存 → 缩到单接口 → 缩到单函数
- 最小化的副产品是回归测试的原型——阶段四它直接变成失败测试

## 阶段三 · 假设与证伪（一次只验一个）

把假设写成**可证伪**的形式：

> 因为 X 在 Z 处做了 Y，所以出现 P。

- ❌「可能是缓存问题」（不可证伪，怎么都算对）
- ✅「缓存命中时直接读了旧字段、跳过刷新逻辑——清缓存后现象应消失」（可证伪）

验证规则：

1. **一次只验一个假设**。同时改两个变量 = 两个结论同时作废
2. **用最便宜的实验证伪**：加日志 < 打断点 < 一次性脚本 < 改产品代码。倒着用这个顺序是最大的浪费
3. **证伪了就记录**。排除清单和命中清单一样值钱——它收窄下一个假设的空间
4. 候选空间大就用**二分**：`git bisect` 找提交、代码路径二分、数据集二分。二分的每一步必须有观测点——观测不到差异的二分是盲切

## 阶段四 · 修复与回归闭环

- **修根因不修症状**：回到 `intake.md` 的症状 → 真源映射表，确认改的是真源那一层
- 修复必须回答反向变异：把修复去掉，阶段一那条复现路径会怎样？说不出 = 没验证
- **复现路径固化为守卫**：阶段二的最小用例 → 失败测试（红）→ 修复（绿）→ 测试留在套件里（见本技能「测试先行」）。这次学到的路径，下次由机器拦
- 复盘三问照常走，不因「找到了根因」而豁免

## 反模式

| 反模式 | 为什么坏 |
|---|---|
| 猜修（change-and-pray） | 改了三处现象消失：不知道哪处起效，不敢删另两处，代码带着两处死改动 |
| 调试中顺手重构 | 结构一变，之前的观测全部作废，等于重新开始 |
| 修症状 | 下次换个入口再发作；见 intake.md 症状 → 真源表 |
| 无复现就改 | 修完无法验证，等于把结论交给上线环境抽签 |
| 「看起来修了」 | 没跑阶段一的复现路径就宣布完成——这与「没修」在证据上无区别 |

## 自查三问

1. 复现路径能交给别人独立跑吗？
2. 用例最小化了吗？（还能再砍一刀吗？）
3. 每个假设是被**证伪实验**排除的，还是「看起来对」？

三问都「是」，才允许进入修复。
