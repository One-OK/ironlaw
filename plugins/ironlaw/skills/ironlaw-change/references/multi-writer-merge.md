# 多写者并行合并协议

## 适用场景

- 第二个人 / 第二个 Agent / 第二条发布线在同一个仓库动代码
- 长时间任务期间远端持续前进
- 你有未提交的半成品，同时要拉远端

## 铁律

1. **权威 tip 只认远端**：`git ls-remote origin refs/heads/main`。本地 `origin/main` 会冻结，本机 `git log` 看到的可能是几小时前的世界。
2. **永不 force push**。永不整文件"取一边覆盖"——那会静默删掉对方刚修的东西。
3. **合并后必须重跑门禁**，因为合并本身改变了代码。

---

## 开工对账（每次动手前，只读）

```bash
git ls-remote origin refs/heads/main      # 远端真实 tip
git rev-parse HEAD                        # 本地 tip
git status --short                        # 未提交改动
git log --oneline -5                      # 本地最近提交
```

三项判读：

| 情况 | 处置 |
|---|---|
| 远端 == 本地，工作区干净 | 直接开工 |
| 远端领先 | 先看差了什么（`git diff --stat HEAD..origin/main`），再决定是否先合并 |
| 远端领先且改了你要改的文件 | **先合并再改**，否则你会在旧世界写完再撞一次 |
| 有发布锁 / 部署进行中 | 等，或只做只读工作 |

还要看：有没有别的进程在跑（部署/门禁/构建），有没有陈旧锁文件。

---

## 合并四步（快进优先）

### 第 1 步 · 判定能否快进

```bash
git fetch origin main
git merge-base --is-ancestor HEAD origin/main && echo "FF 可行"
```

- **FF 可行** → `git merge --ff-only origin/main`，历史干净，不改写任何 sha
- **FF 不可行**（远端有你没有的提交，你有远端没有的提交）→ 走第 2 步

> 用 `merge` 而不是 `rebase`：rebase 会改写你的提交 sha，而变更档案/台账/门禁可能已经引用了那个 sha，改完就对不上。

### 第 2 步 · 未提交改动先做 WIP 快照

```bash
mkdir -p .workbuddy/artifacts/wip-$(date +%Y%m%d)
cp --parents <每个改动文件> .workbuddy/artifacts/wip-$(date +%Y%m%d)/
git stash push -u -m "wip-$(date +%Y%m%d-%H%M)"
git merge --ff-only origin/main
git stash pop
```

快照的作用不是备份，是**事后举证**：证明合并后你的改动逐字节保留了。

### 第 3 步 · 撞文件按内容叠加

冲突文件**逐个**处理，规则：

| 文件类型 | 处理方式 |
|---|---|
| 两边都改了同一段 | 读两边意图，合成第三版（不是二选一） |
| 一边改结构、一边改文案 | 保结构 + 叠文案 |
| 台账/登记类 | 按时间序**两边都保留**，不覆盖 |
| 锁文件（package-lock 等） | 取更完整的一方，然后重跑安装并验证可复现 |
| 自动生成物 | 重新生成，不要手工合 |

**禁止** `git checkout --ours/--theirs <整个文件>` 作为默认手段。

### 第 4 步 · 举证保留 + 重跑

```bash
# 对每个改动文件比 md5
md5sum .workbuddy/artifacts/wip-*/<path> <path>
```

预期：除了你**故意**叠加的那几个冲突点，其余逐字节一致。差异必须能逐条解释。

然后重跑：

1. 定向守卫（针对你改的东西）
2. 全量门禁（因为合并引入了别人的代码）

## 台账类文件的叠加写法

台账/STATUS/CHANGELOG 是"追加型"文件，两边同时追加是最常见的冲突。

正确姿势：**按时间序插入，两边都保留**。

```
| 14:09 | 对方线 | ... |
| 14:16 | 本线   | ... |   ← 插在 14:09 之后，不删除对方行
| 14:18 | 本线   | ... |
```

做法：把本线新增行快照下来 → 合并远端 → 在自己最后一条之后插入对方行 → 复核守卫。

**不要**用"保留我方全部"——会把对方的登记整段吞掉，而台账守卫只检查"最新版本有没有登记"，未必能发现中间少了行。

## 常见坑

| 坑 | 表现 | 处置 |
|---|---|---|
| 本地 origin/main 冻结 | 以为远端没动，推的时候被拒 | 只用 `ls-remote` 判远端 |
| 在 bump 提交上直接部署 | 部署前置闸拒绝 | 顺序：合并 → 出包 → 台账 → 部署 |
| 合并后忘记重跑 | 门禁是合并前的结论 | 合并 = 代码变了 = 重跑 |
| 用 `-X ours` 批量解决 | 对方修复静默丢失 | 逐个文件按内容叠加 |
| 锁文件取一边 | CI 装不上 | 取完整树 + 重装 + 验证 `npm ci` 可复现 |
| 陈旧锁没清 | 自动链永远"部署进行中" | 确认无进程后清锁（记录时间戳） |

---

## 一句话总结

> 合并的目标不是"让 git 不报错"，是**两边的工作都留下，并且能被证据证明留下了**。
