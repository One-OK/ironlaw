# 验证设施免责：先证明"尺子没坏"

## 为什么这条排在第〇段

任何 FAIL 出现时，人的默认动作是"去改代码"。但如果失败来自验证设施（测试框架/浏览器驱动/构建缓存/环境变量），你改的是健康代码——**同时把真缺陷挤出了注意力**。

真实代价：一次全量跑 26 个场景 9 个 FAIL，逐个单跑 **9/9 全过**。根因是浏览器复用未重置。如果当时去"修产品"，会改动 9 个本来正确的模块。

---

## 判别三连（按序，不许跳）

### 1. 单独重跑

同一断言/场景单独跑：

| 结果 | 结论 |
|---|---|
| 单跑过、批量不过 | **设施污染**：跨场景状态、冷启动竞态、监听器泄漏、共享页面 |
| 单跑也挂 | 进入第 2 步，别急着定性为产品缺陷 |
| 单跑超时 | 先看第 3 步，再看资源（内存/端口/锁） |

### 2. 时间线取证

```bash
git log --oneline --since="<上次通过的时间>" -- <相关目录>
```

- 区间内**零相关改动** ⇒ 大概率数据漂移或设施抖动，不是这次改动坏的
- 区间内有相关改动 ⇒ 仍需第 3 步确认是不是"改动本身没问题但触发了脆弱断言"

### 3. 前序 soft 项

看失败项的上一条：如果它是 `soft` / `△ 超时` / `⚠ 跳过`，失败很可能是它的连带后果。先重跑那一条，再判断当前这条。

---

## 数据漂移 vs 代码回归

第三条独立判据，专门处理"代码没动，断言红了"。

**问：断言依赖的数据前提现在还成立吗？**

| 现象 | 定性 | 处置 |
|---|---|---|
| 样本被别的流程推进了状态（DRAFT→已核价），入口按设计隐藏 | 数据漂移 | 修断言维度（加业务状态筛选），不改产品 |
| 断言写死"该记录应为 0 条"，有人录了一笔 | 期望值过期 | 改成"与接口实时计数一致" |
| 全库已无合格样本 | 无法断言 | 降级为 soft（显式声明），不硬红 |

### 断言的正确形态

```
❌ 写死快照：expect(count).toBe(0)
✅ 钉规则：实时读接口 _count，断言"徽标 0 不挂、>0 挂 N 且等于接口值"
```

> 断言钉**规则**，不钉**数据快照**。钉快照的断言是定时炸弹。

### 判据前提必须显式

断言依赖"必须有 N 条满足条件的样本"时：

- 显式声明为 soft：无样本 → skip 且**在报告里单独可见**
- 或者从接口实时取，不预设

二者都不做 = 定时假红。

## 三态收口（比"通过/失败"多一维）

| 态 | 含义 | 退出码约定 |
|---|---|---|
| PASS | 跑了且过 | 0 |
| FAIL | 跑了且不过 | 1 |
| SKIP | 没跑（缺样本/缺凭据/设施不可用） | 需单独可见 |
| SUSPECT | 全量失败但单跑通过 = 疑似设施 | 3 |

**SKIP 不许计入 PASS 数。** 一个报告写"21/21 通过"而其中 3 个是跳过的，等于谎报。

### 禁止的写法

```
if (缺样本) { pass++; }              // 假绿
if (缺样本) { fail++; }              // 假红（用户被无意义红灯训练成忽略红灯）
if (缺样本 && 上次过了) { pass++; }   // 最坏
```

### 正确写法

```
if (缺前置) { skip('缺 X 前提'); return; }   // 单独计数、单独展示
```

## 检查清单

出现红项时，按顺序回答：

- [ ] 单跑这条能过吗？
- [ ] 相邻两次运行之间 `git log` 有相关改动吗？
- [ ] 失败前一条是不是 soft/超时/跳过？
- [ ] 断言依赖的数据前提还成立吗？
- [ ] 有没有可能是并行进程/另一条发布线在重启服务？

五问全否，才动产品代码。**答案要写进提交信息或变更档案，不许口头豁免。**
