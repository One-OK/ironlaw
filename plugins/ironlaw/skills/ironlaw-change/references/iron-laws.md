# 四条铁律详解

这四条不是价值观，是**用真实事故换回来的判定方法**。每条都带"怎么验"，因为不验的规范等于没有。

---

## 铁律一 · 「必填」必须 fail-closed

### 判据只有一条

把这条机制**喂空数据**跑一次，放行就是不存在。

空数据的六种形态，每一种都要单独想：

| 空形态 | 典型代码 | 正确行为 |
|---|---|---|
| 空数组 | `if (!records.length) return 0` | 若"必然应有记录"则判红；若"合法可为空"则判绿 **但必须写理由** |
| 缺章节 | `if (!section) continue` | 缺 §2.5 且动了产品源码 → 判红 |
| 缺文件 | `if (!existsSync(p)) return` | 缺台账/缺基线 → 判红并点名路径 |
| 缺参数 | `opts?.mode ?? 'default'` | 默认值只能有一处；第二处默认值等于第二套口径 |
| 超时 | `status === 0`（null 被当成功） | `status === null` 必须显式判红并标注"设施超时" |
| 异常 | `try { } catch { }` | 必须至少 `console.error` 一行原因，禁止静默吞 |

### 真实事故形态

生成器不产出某章节 → 检查器对"缺该章节"判 OK → 12 份档案里 7 份没有该章节 → 其中一份跨四个包、删了 7 个端点，推送门禁全绿。

三处同时失效，且**互相掩护**：人看到的是"全绿"，读到的是自己脚本的输出。

### 自查一句话

> 我这条判据，如果今天什么都还没做，它会不会也判绿？

会 → 它守的不是"做了"，是"没崩"。

## 铁律二 · 每条新守卫必须自带反向探针

### 只有正向探针 = 没有守卫

"喂正确数据 → 通过"分不清"实现了"和"没实现"。必须有一条：

> 把保护去掉 → 必须转红。

### 必须用快照还原法做变异

```
cp 原文件 备份
变异（改坏）
跑守卫 → 断言转红
cp 备份 回原文件
md5 逐字节比对 → 必须一致
```

**禁止用"反向字符串替换"复原**——替换会漏掉空白/行尾/大小写差异，你以为复原了，其实留了污染。用 `md5` 或 `sha256` 比对，比对结果要打印出来。

工具：`ironlaw-gate` 技能的 `scripts/reverse-probe.mjs` 直接做这件事（含变异命中数校验、自动复原、md5 断言）。

### 探针要覆盖"跳过"这条路径

最阴的假绿不是"判据写错"，是"**没跑却计通过**"：

```
if (真实资源被占用) { log('跳过'); pass++; }   // ← 假绿
```

正确写法：探针必须用**隔离资源**（唯一路径/唯一端口/唯一临时库），永不因本机状态跳过；跳过只能是"设施不可用"且必须单独可见，不能计入通过数。

### 反向变异清单（每条守卫至少一组）

| 变异 | 期望 |
|---|---|
| 删掉判据核心分支 | 转红 |
| 判据改成永远 true | 转红 |
| 把 fail-closed 改成 fail-open | 转红 |
| 把超时预算调到 1ms | 转红（而不是"跳过仍绿"） |
| 换掉共享判据、改回本地副本 | 双副本守卫转红 |

## 铁律三 · 跨脚本口径单一真源

### 什么必须收口

- "什么算产品源码"（目录白名单/扩展名）
- "范围键怎么归"（模块→键的映射）
- "谁算豁免"（白名单/注释标记）
- "失败行长什么样"（诊断行正则）
- "版本号从哪读"（哪个文件是版本真值）
- "默认值是多少"（同一参数的第二处默认值）

### 两份的错位方向通常是"互相掩护"

A 认为"没触及"→ 不要求；B 认为"触及了"→ 也没人看。两边都松，用户看到全绿。

### 落地形态

```
scripts/lib/
  impact-scope.mjs      # 产品口径 + 范围键 + 覆盖判定
  gate-runner.mjs       # 失败行抽取 + EXIT 码 + 熔断
  version.mjs           # 版本真值读取
```

各脚本只 `import`，禁止复制粘贴。**发现有第二份时，先收口再修 bug**——否则你修的那份可能不是真正生效的那份（典型：默认参数写在策略函数里，但调用方永远显式传值，策略里那份默认值永不生效）。

### 怎么证明收口了

grep 同一段正则/同一个字面量，全仓命中数应为 1（或 1 处定义 + N 处 import）。

## 铁律四 · 影响链靠机器算的覆盖率

### 人脑枚举的漏项是系统性的

不是随机漏，而是**总是漏自己不熟的那一侧**。真实案例：跨 api/web/mobile/shared 四包的改动，人脑清单漏了 mobile 与 shared——后者正是授权商业真值所在。

### 做法

1. 机器先算"本次 diff 触及哪些范围键"（按模块/目录聚合）
2. 每个键必须二选一闭环：
   - 写一条机器可跑的断言（正则 + 范围 + 期望计数）
   - 或给出 ≥8 字的不适用理由
3. **漏的键点名**，不许汇总成"其余已检查"

### 断言必须能真跑

写成 markdown 表格，由脚本执行：

| # | 断言 | 检索式（JS 正则） | 范围 | 期望 |
|---|---|---|---|---|
| 1 | 付费页先刷授权再判门控 | `await refreshLicense\(\)` | `apps/mobile/src/pages` | `>=4` |
| 2 | 旧实现零残留 | `deferredLoad\(` | `apps/mobile/src` | `=0` |

`>=N` 用于"必须存在且达到规模"，`=N` 用于"精确计数"，`=0` 用于"零残留"。三种就够，不要发明第四种。

工具：`ironlaw-record` 技能的 `scripts/verify-record.mjs` 直接执行这张表。

## 复盘三问（展开）

### 第 1 问：哪一环没做

必须定位到**机制**，不是人。

- ❌ "我忘了跑门禁"
- ✅ "门禁只在 pre-push 跑，而我这次是手工 `git push --no-verify`，没有第二处拦截"

### 第 2 问：为什么没做

三选一，处置完全不同：

| 答案 | 处置 |
|---|---|
| 不知道 | 补文档 + 补到开工检查表（最轻） |
| 来不及 | 说明流程成本过高，需要削减步骤或自动化，而不是要求"下次挤时间" |
| **机制允许** | **最重**：改机制，让它物理上做不到 |

绝大多数事故是第三种。用户说"你又没考虑清楚就上线"，根因往往是"系统允许不考虑清楚就上线"。

### 第 3 问：机制改了什么

必须是可核验的：

- ❌ "下次更仔细"
- ❌ "已记录到规范"
- ✅ "提交信息缺三段 → pre-push 拒绝推送"
- ✅ "缺 §2.5 且触及产品源码 → 检查器返回 1"
- ✅ "新增反向探针 3 条，改坏任一处守卫转红"

### 第 3 问答不出来时

回到第 1 问。答案不是"我记住"，就还没找到机制。
