# 上线闭环：真值只认外部可观测事实

## 一句话原则

> **「推送成功」不等于「上线了」；「部署脚本 exit 0」不等于「服务在服务」。**
>
> 真值只认三样：远端分支指针、线上接口返回的版本号、分发通道的 manifest。

## 发版的定义

| 动作 | 算不算发版 |
|---|---|
| `git commit` | 不算 |
| `git push` | **不算**，只推进代码托管 |
| 版本号 bump | 不算 |
| 构建产物上传到分发通道，且 manifest 登记为 `published` | **算** |

真实事故形态：一天 push 七次、版本从 0.22.46 涨到 0.22.53，而分发包始终是 0.22.46，持续 19 小时。用户质问"都 22.53 了，包里还是 22.46，你们到底有没有遵循发布规则"。

根因不是"忘了"，是**规则缺口**：写了"每次 push 必须 bump"，没写"bump 之后必须出包"。而部署脚本里那句"欠了 N 个版本"被 `|| echo "[SKIP]"` 静音了。

## 七步顺序铁律

```
① bump 版本（三处同步，只用脚本：脚手架自带 scripts/bump-version.mjs，禁止手改）
② commit（三段式提交信息）
③ push（safe-push：对账 + 快进合并 + 推送 + 三判据；脚手架自带 scripts/safe-push.sh）
④ 全量门禁（合并了远端就必须重跑）
⑤ 出包 + 上传 + 双核验（旧版本号能拉到新版 / 新版本号 204）
⑥ 台账登记（版本 / 基线 / 产物指纹）→ 提交推送
⑦ 部署 → 部署后复验 → 回填证据 → 再推送
```

### 为什么顺序不能变

| 颠倒 | 后果 |
|---|---|
| 先抄台账再部署 | 部署前对账发现"台账已写但线上没变"，或台账版本落后被守卫拦 |
| 在 bump 提交上直接部署 | 部署前置闸拒绝（HEAD 停在"只改版本号"的提交上） |
| 出包前不跑门禁 | 发出去的包带着红 |
| 部署后不核对接口 | 以为上了，其实 nginx 缓存/旧容器还在服务 |

### 版本号纪律

- 三处（根 / 前端 / 后端）必须同号
- **只用脚本 bump**，手改是"三处不一致 + BOM + merge 冲突标记"的共同根源
- 格式固定位宽（不足补零），否则排序会错

## 推送三判据

推送后必须三条都过，缺一条就不算成功。优先用脚手架自带的 `scripts/safe-push.sh`（它自动做这三条核对并输出 `PUSH_RC` / `REMOTE_TIP` / `LOCAL_TIP`）；手工推送时逐条核对：

```bash
# 1. 单独捕获退出码（不要用管道，$? 会被管道最后一环覆盖）
git push origin HEAD; RC=$?; echo "PUSH_RC=$RC"
# 2. reflog 确认本地记录的 origin 指针前进
git reflog show origin/main | head -1
# 3. 权威真值：远端实际指针
git ls-remote origin refs/heads/main
```

**第 3 条是唯一权威。** 本地 `origin/main` 会冻结——你看到"已同步"，远端可能已经又前进了。

## 真值源矩阵

| 问题 | 错误来源 | 正确来源 |
|---|---|---|
| 代码推上去了吗 | 命令行无报错 | `git ls-remote` |
| 线上跑的是哪版 | 部署脚本的日志 | `GET /api/config`（或同等 health/version 接口） |
| 客户机拿到的是哪版 | 打包脚本输出 | 分发通道的 `updates/check` 返回的 manifest |
| 台账和实际一致吗 | 台账自己 | 台账 vs `package.json` vs manifest 三方比对 |
| 包里是不是这次的代码 | 构建日志 | 拉取线上入口 chunk，grep 本版新增/删除的字符串 |

## 部署后复验（三层）

只做第 1 层 = 只证明"没崩"。

### 第 1 层 · 产物与进程

- 线上入口文件路径与本地构建产物一致
- 服务进程健康（health 接口 200）
- 版本接口返回 HEAD 的版本

### 第 2 层 · 页面级只读

- 遍历主要页面，全部能打开、无 JS 报错、无空白
- 判定"通过 / 警告 / 失败"三档，警告不许混进通过数

### 第 3 层 · 真实交互

- 改列表/分页 → 真浏览器翻页、搜索、切换视图
- 改表单 → 提交、回读、确认落库
- 改样式 → 截图比对

**只读断言不等于交互验证。** 新增的写路径必须在上线前走完整闭环，不能等用户点名才补。

### 产物指纹双向 grep

```bash
HTML=$(curl -s https://<host>/)
ENTRY=$(printf '%s' "$HTML" | grep -o 'assets/index-[A-Za-z0-9_-]*\.js' | head -1)
curl -s "https://<host>/$ENTRY" -o /tmp/entry.js
grep -c '<本版新增的版本号或新符号>' /tmp/entry.js   # 期望 >=1
grep -c '<本版删除的文案>' /tmp/entry.js             # 期望 =0
```

一正一反两条，才能证明"线上跑的是这次构建"，而不只是"版本号对了"。

## 自动链与抑制

若仓库配了"push 后自动部署"的链条：

- 它会与你的手工顺序冲突（在 bump 提交上部署、与你抢锁）
- 需要手工控制顺序时，用环境变量抑制：`AUTO_DEPLOY=0 bash scripts/safe-push.sh ...`
- 抑制后必须自己把部署做完，否则欠账会挂在门禁上

判断链条是否在跑：看进程、看状态文件、看锁文件的时间戳。**陈旧锁**会让后续所有部署误判"正在进行中"——确认无进程后清理，并记下时间戳。

## 发布锁与发布权

| 机制 | 作用 | 注意 |
|---|---|---|
| 互斥锁 | 防止两条线同时部署 | 锁文件通常是本地运行态，重装/换工作树会丢；陈旧锁要清 |
| 发布权 | 绑定"哪个工作区有权发布" | 防多线互相覆盖；文件丢失时必须在**真正部署前**确立，不要跳过守卫 |

不确立发布权就绕过 = 两条线的产物互相覆盖，且事后无法定位是谁覆盖的。

## 回滚

上线前就要写好，不是出事时想。

| 层 | 回滚动作 |
|---|---|
| 代码 | `git revert <sha>` 或部署上一个 tag |
| 数据 | 迁移的逆操作（**必须提前验证过**） |
| 配置 | 恢复旧环境变量 / 旧 manifest |
| 分发 | 把 manifests 里旧版本重新标记为 published |

**唯一不可回滚的是已经发给客户机的数据迁移**——所以涉及迁移的版本，回滚方案必须在部署前演练过。

## 用工具核验

```bash
node scripts/ship-truth.mjs --config ship.json
```

核验六项：版本一致 / 工作区干净 / 本地=远端 / 线上版本 / 分发版本 / 台账登记。

退出码 0 全部一致，1 有真值不一致，2 **无法取得真值**（网络/配置）。

> 「取不到真值」必须与「通过」区分。很多"部署成功"的报告，其实是网络超时后默认放行。
