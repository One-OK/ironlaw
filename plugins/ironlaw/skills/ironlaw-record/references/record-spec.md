# 七段逐段要求

每一段都有"合格 / 不合格"的判据。不合格的档案会在推送前被拦，或者更糟：被放过，然后在事故复盘时发现它什么都没说明。

---

## 0 改动范围

**机器生成，不要手写。**

手抄的清单几乎必然漏文件——人对"我改了哪些"的记忆是按主题组织的，不是按路径。

合格：

```
涉及文件：
- apps/api/src/x.service.ts
- apps/mobile/src/pages/orders/index.vue
```

不合格：`改了订单相关的一些文件`。

---

## 1 根因

### 必须写成一句可证伪的话

> 根因是 **X**，不是 Y。

- 合格：「根因是**入口列序定义按字母序生成，而人读的顺序是业务流顺序**；不是排序函数写错了。」
- 不合格：「修复了列表排序问题。」

### 至少往上追一层

用户报的是**症状**。症状 → 真源往往隔一层：

| 用户说 | 表面 | 真源 |
|---|---|---|
| 列顺序反了 | 排序函数 | 列序定义的人读顺序 |
| 金额对不上 | 计算 | 币种口径（对客 vs 内部） |
| 时间差 8 小时 | 格式化 | 本地时间被拼成 UTC 字符串 |
| 基础版还能用付费功能 | 按钮没隐藏 | 生命周期没判授权，先发了请求 |
| 手机上打开是空白 | 白屏 | 域名没进白名单 |

### 反例特征

- 出现「优化」「完善」「调整」等无法验证的词
- 描述的是"我做了什么"而不是"为什么会这样"
- 一句话里塞了三个原因（说明还没找到主因）

## 2 影响链

### 六类必须逐项表态

即使某一类"没触及"也要写"未触及"，因为**没写就等于没想过**。

| 类 | 自查命令 |
|---|---|
| 渲染 | `grep -rn "<符号>" --include=*.vue --include=*.tsx src/` |
| 契约 | 查 DTO / 共享类型包 / 接口定义 |
| 产物 | 查 PDF / 导出 / 打印 / 邮件模板 |
| 测试 | `grep -rn "<旧行为关键词>" --include=*.spec.ts test/` |
| 文档 | 台账 / 设计文档 / 注释旧名 |
| 联动 | watch / 派生 / ensure* 同步 / 缓存失效 |

### §2.5 是这一段的"证据"

没有 §2.5 的影响链是"我搜了一下"，有 §2.5 的是"我搜了并且钉住了"。

### §2.6 的写法

机器算出的每个范围键必须二选一闭环：

- 被 §2.5 某条断言覆盖
- 或在 §2.6 给 ≥8 字理由

合格的 §2.6：

```
- `docs/`：本次只追加台账登记行，不涉及行为变更，无需断言。
```

不合格：

```
- 其余已检查
```

「其余」= 没检查。

## 3 未修点与理由

**几乎每次改动都有"这次不做"的项。** 写"无"通常意味着没认真找。

| 列 | 要求 |
|---|---|
| 未修点 | 具体到现象，不是"部分场景" |
| 为什么不修 | 决策理由（ROI / 依赖外部 / 需要产品拍板） |
| 何时处理 | 具体触发条件（下个版本 / 有用户反馈 / 等上游开放字段） |

价值：三个月后有人问"为什么这里没处理"，答案在档里，不用重新推理一遍。

---

## 4 用户可见影响与恢复路径

三段：

1. **会看到什么变化**（哪怕是"没有变化"也要说清为什么）
2. **出错时的现象**（让支持人员能识别）
3. **用户自助恢复方式**（刷新？重登？换入口？）

不合格：「无影响」——除非真的没有用户可见面，且要说明依据。

---

## 5 回滚方案

必须具体到可执行：

```bash
git revert <sha>
# 若含数据迁移，写逆迁移
# 若含配置变更，写回滚后的配置值
```

不合格：「回滚代码即可」——数据迁移不可逆时这句话会害人。

**判断标准**：凌晨两点，一个没参与本次开发的人，能不能照这段文字把系统恢复？

---

## 6 验证证据

### 三段式

| 项 | 命令 | 结果 |
|---|---|---|
| 类型检查 | `npx tsc --noEmit` | 0 error |
| 单测 | `npx jest --runInBand` | 412 passed |
| 全量门禁 | `bash run-gate.sh` | EXIT=0（645s，18/18） |

### 产物指纹

构建/部署类改动必须给：

- 入口文件路径
- 文件大小
- 哈希（sha256）
- 版本号

### 线上真值

部署后必须给**接口返回的真实值**，不是"部署脚本说成功了"。

> 「脚本 exit 0」≠「服务在服务」。判据是接口返回的版本号与预期一致。

---

## 7 完成判据

### 三层结构

| 列 | 回答什么 |
|---|---|
| 修复项 | 用户/需求视角的一条 |
| 全不全判据 | 完备性的**机械事实**（计数、差值、集合相等） |
| 验证证据 | 哪条断言/哪一步门禁/哪次真机验证 |
| **负控制** | **改坏什么 → 哪条转红** |

### 负控制为什么必须单独一列

「验证证据」证明"现在是对的"；「负控制」证明"这个验证真的会红"。

只有前者，你无法区分：

- 断言真的在守
- 断言写错了范围，永远零命中，永远绿

### 合格写法

```
| 3 | 到期日时区 | `dueAtOf(` >=2 且落本地 09:00 | mobile tsc + 双端构建 | 改回 `${dueDate}T09:00:00.000Z` → 守卫 C 组判红 |
```

### 不合格写法

- 「构建会报错」（没说哪条）
- 「已加守卫」（守卫可能是假的）
- 「理论上会红」（没跑过）

### 写不出来时

说明这一项没有被验证。要么补一条能被改坏的断言，要么在 §3 承认它没验证——**不要用形容词填满空格**。
