# 影响链断言文法

## 表格格式

```md
| # | 断言 | 检索式（JS 正则） | 范围 | 期望 |
|---|------|------------------|------|------|
| 1 | 一句话说明守什么 | `正则` | 目录A 目录B | >=2 |
```

解析规则（`verify-record.mjs` 的实现口径）：

- 表头可为任意文字，按列序取第 2/3/4/5 列
- 检索式取**反引号内**内容；无反引号则整格当正则
- 范围按空格/逗号切分，可写多个目录或具体文件
- 期望只接受 `>=N` / `=N` / `<=N`（`N` 可省写为 `N`，等价 `=N`）

---

## 期望的三种语义

| 期望 | 语义 | 什么时候用 |
|---|---|---|
| `>=N` | 至少 N 行 | 防御性断言：必须存在，且达到规模（防"只改了一个页面"） |
| `=N` | 恰好 N 行 | 唯一性断言：唯一出口、唯一路由、唯一默认值 |
| `=0` | 零命中 | 清理性断言：旧实现删净、禁词清零 |

**没有第四种。** 出现「大约」「至少大部分」「应该」这类词，说明还没想清楚要钉什么。

---

## 计数的单位是"行"

一行命中一次也算 1，一行命中五次也算 1。

原因：档案里写"实际 6 行（>=4）"是可读的；写"实际 23 次匹配"没人能核对。

**推论**：不要把多个判定塞进同一个正则的多个 `|` 分支——那会让计数失去意义。拆成多行断言。

---

## 正则写法

### 转义

表格里写的是 **JS 正则源码**，不是字符串字面量：

| 想匹配 | 写 |
|---|---|
| `refreshLicense()` | `refreshLicense\(\)` |
| `${base}/leads/${leadId}` | `\$\{base\}/leads/\$\{leadId\}` |
| `phone=${phone}` | `phone=\$\{phone\}` |
| 引号字符串 | `"widget"` 或 `["']widget["']` |

### 窄到什么程度

判据：**能让它命中的，是否只有你真想守的那一处？**

| 写法 | 问题 |
|---|---|
| `phone` | 命中所有含 phone 的行（几十上百），计数失去意义 |
| `phone=` | 仍可能命中赋值、比较、日志 |
| `phone=\$\{phone\}` | 只命中裸打印那一处 ✓ |

### 多行匹配

默认逐行匹配。需要跨行时不要在表格里写 `[\s\S]*`——那会让计数变成"整文件算 1 行"。

改为：分别写"开头存在"和"结尾存在"两条断言。

## 范围写法

```
apps/mobile/src/pages              # 目录（递归）
apps/mobile/src/pages/orders       # 更窄的目录
apps/api/src/a.ts apps/api/src/b.ts  # 多个具体文件
```

### 范围必须存在

`verify-record.mjs` 对"范围全部不存在"直接判红。这条是故意的：

否则写错路径的断言会永远零命中，而 `=0` 类断言就变成永真式——**这是最隐蔽的假绿**。

### 排除

不支持在表格里写排除规则。需要排除时，把范围收窄到具体子目录，或在该目录下用更窄的正则。

---

## 常见错法

| 错法 | 后果 | 修法 |
|---|---|---|
| 范围写成 `src` 但项目用 `apps/web/src` | 范围不存在 → 判红（好的）；或范围存在但扫不到目标 → 计数 0 | 核对真实路径 |
| `=0` 断言的范围包含了测试文件（里面留着旧字符串） | 永远红，然后被注释掉 | 范围排除 test，或把断言拆成"生产代码 =0 / 测试允许" |
| `>=1` 断言写了个必然存在的词（如 `import`） | 永远通过，没有信息量 | 换成"本次新增的符号" |
| 断言描述写成"已修复 X" | 读不出守的是什么 | 写成"X 的新写法存在于 Y 处" |
| 用一个断言覆盖五个改动点 | 一条红不知道是哪处 | 一个改动点至少一条 |

## 断言数量

| 改动规模 | 建议断言数 |
|---|---|
| 单文件小修 | 2~3 条（存在 + 零残留） |
| 多文件同主题 | 5~8 条 |
| 跨包/跨端 | 10~15 条，每个范围键至少一条 |
| 超过 20 条 | 考虑拆成多份档案，或说明为什么必须一次做完 |

**断言数不是越多越好。** 20 条里有 15 条是 `>=1` 的"存在性"断言，说明没有在设计判据，只是在凑数。

好的分布：每个改动点一条"新写法存在"，加一条总体的"旧写法零残留"。

---

## 自检三问

1. 把对应代码删掉，这条会红吗？
2. 把断言范围改成一个不存在的目录，我的期望值会不会"碰巧也成立"？
3. 这条断言红了，读它的人能不能立刻知道去哪个文件看？

三问都"是"，这条断言才算写对。
