# 变更档案：把"我说改好了"变成"机器能验"

## 为什么要有这个东西

代码 diff 只说明**改了什么**，不说明**想清楚了多少**：

- 根因是不是真源？（还是把症状按下去了）
- 影响链有没有漏？（那六类里总有一类是你平时不看的方向）
- 改坏了谁会红？（说不出 = 没验证）
- 怎么回滚？（上线出事时的第二小时）

档案的作用不是留痕给审计看，是**在提交前逼自己把这四个问题答完**，并且答案能被脚本执行。

## 什么时候必须写

| 情况 | 要不要写 |
|---|---|
| 改了产品源码（前后端/移动端/共享包） | **必须** |
| 只改文档/脚本，未触发版本 bump | 不必单独写 |
| 同族小修（同一主题的后续修补） | **不另开新档**，在原档案加第二行 `tip: <新 sha>` |
| 纯格式化 / 纯注释 | 不必，但提交信息仍要三段 |

判据由机器算：本次 diff 触及了哪些「范围键」（按模块聚合），每个键必须被一条断言覆盖，或给出理由。

## 七段（缺一段即不合格）

| 段 | 写什么 | 不合格长什么样 |
|---|---|---|
| 0 改动范围 | 机器生成（提交列表 + 文件列表），不要手写 | 手抄漏文件 |
| 1 根因 | 一段话：**根因是 X，不是 Y** | 「修复了一些问题」 |
| 2 影响链 | 六类逐项（渲染/契约/产物/测试/文档/联动），含 §2.5 断言表、§2.6 不适用理由 | 只写「已全局搜索」 |
| 3 未修点与理由 | 明知没修的点，逐条写为什么 + 何时修 | 假装没有 |
| 4 用户可见影响与恢复路径 | 用户会看到什么变化；出问题怎么恢复 | 「无」但不解释 |
| 5 回滚方案 | 具体到命令/提交/数据迁移的逆操作 | 「回滚代码即可」 |
| 6 验证证据 | 真正跑过的命令 + 输出摘要 + 产物指纹 | 「本地测试通过」 |
| 7 完成判据 | 逐项销账表，**必须含「负控制」列** | 只写「已修复」 |

## §2.5 断言表：核心

一张能被脚本执行的表：

```md
| # | 断言 | 检索式（JS 正则） | 范围 | 期望 |
|---|------|------------------|------|------|
| 1 | 付费页先刷授权再判门控 | `await refreshLicense\(\)` | apps/mobile/src/pages | >=4 |
| 2 | 旧实现零残留 | `deferredLoad\(` | apps/mobile/src | =0 |
| 3 | 深链走真实路由 | `\$\{base\}/leads/\$\{leadId\}` | apps/api/src/assignment | =1 |
```

**期望只有三种算子**（校验器只接受这三种，裸数字按 `=N` 处理），不发明第四种：

- `>=N` —— 必须存在且达到规模（防"只改了一个"）
- `=N` —— 精确计数（唯一出口、唯一路由）；`=0` 是 `N=0` 的特例：零残留（删干净、禁词清零）
- `<=N` —— 上限断言（防增殖：待接入点、白名单条目只减不增）

### 三条硬要求

1. **按行计数**，不按匹配次数。`g` 标志只为逐行匹配，计数单位是行。
2. **范围必须是真实目录**。范围不存在 → 判红（不许因为路径写错而"零命中通过"）。
3. **正则要窄到只有目标会中**。写 `phone` 会命中 200 行，写 `phone=\$\{phone\}` 只中 1 行。

详细的写法细则与常见错法见 `references/assertion-grammar.md`。

## §7 完成判据：负控制列

这一列是**这次改动最容易被跳过、也最值钱的一列**。

```
| # | 修复项 | 全不全判据 | 验证证据 | 负控制（改坏什么→哪条红） |
```

负控制必须写成：**改坏 X → Y 转红**。

- ❌ 「构建会报错」（没说哪条断言）
- ❌ 「已加守卫」（守卫本身可能是假的）
- ✅ 「改回 `${dueDate}T09:00:00.000Z` → 守卫 C 组判红」
- ✅ 「去掉 `@scope/pkg` → 第 18 步 `check:mobile` 转红（报 X 错）」

写不出负控制的项，说明它**没有被验证**，只是"看起来对了"。

## 提交信息：三段

```
<type>(<scope>): <一句话结果>

根因: <机制层面的一句话，不是复述症状>

影响链: <逐项列出改了哪几处，用 ①②③ 编号；写清"没改什么"也有价值>

验证: <跑了什么命令 + 关键输出 + 结论>
```

要点：

- **行首必须是对应关键词**（`根因:` / `影响链:` / `验证:`），机械门禁按行首匹配
- 验证段写**命令与产物**，不写"测试通过"
- 改了门禁脚本本身时，验证段还要写清在哪些 shell 下、跑了第几步

模板见 `assets/commit-msg-template.txt`。

## 校验

```bash
node scripts/verify-record.mjs docs/change-records/<file>.md
node scripts/verify-record.mjs --latest docs/change-records
```

`scripts/verify-record.mjs` 已随 `ironlaw-bootstrap` 脚手架铺进项目（与本技能内的是同一份工具）；没有脚手架的仓库用技能目录里的路径跑。断言「范围」相对仓库根解析——从子目录跑会整批「范围不存在」判红，这是故意的；确需指定时用 `--root <仓库根>`。

校验器会：

1. 检查七段齐全（缺段判红）
2. 检查 §2.5 存在且有断言行（空表按"没写"处理）
3. **逐条执行断言**：正则 × 范围 → 按行计数 → 比对期望
4. 检查 §7 有「负控制」列

退出码 0 通过 / 1 不合格 / 2 参数错误。

> 只检查"有没有写 §2.5"的门禁，会被一行占位表格骗过去。必须执行它。

## 覆盖闭环（铁律四的机器侧）

断言表只证明「写下的断言成立」，不证明「没有漏键」。用 `impact-scope.mjs` 把另一半也交给机器：

```bash
node <skill>/scripts/impact-scope.mjs --base HEAD~1 --record docs/change-records/<file>.md
```

它从 diff 机器算出本次触及的范围键，逐键对照 §2.5 的断言范围与 §2.6 的理由；漏掉的键点名，退出 1。脚手架的 pre-push 已挂 `verify-record`（存在 `docs/change-records/` 即校验最新档案，`PREPUSH_RECORDS=0` 关闭）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 断言写 `=0` 但范围是个不存在的目录 | 永远零命中，永远绿 |
| 断言写宽泛词（`phone`、`status`） | 计数几百，跟没写一样 |
| 六类影响链只写「已全局搜索」 | 漏的正是你不熟的那一侧 |
| §3 写「无」 | 说明没认真找过；几乎所有改动都有"这次不做"的项 |
| §6 写「测试通过」 | 无法复核；要写命令 + 输出 + 指纹 |
| 同族小修另开新档 | 档案碎片化，历史断链 |
