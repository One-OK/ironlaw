01 / THE PROBLEM

“Looks right” and “provably right”
are separated by an entire chain of evidence

It runs. The page clicks. The console is quiet. None of that is proof. What is missing is the answer to one question: after the change, how do you know it is correct?

Looks rightthe default

  • It runs locally, so it counts as done
  • “I checked everywhere else” — with no list
  • Tests are green, but nobody ever saw them go red
  • The deploy script says success; production still serves the old build
  • The same decision rule is implemented in three different files

Provably rightafter IronLaw

  • The root cause is one sentence of mechanism, not a restated symptom
  • The impact chain is a machine-computed coverage list, with missing keys named
  • Every guard was probed: break it, and it must go red
  • Production truth comes from the API response, not the deploy script’s self-report
  • One implementation per rule; everything else calls into it

In one line: stop trusting “I think it’s fixed.” Either a machine can check it, or it did not happen.

02 / THE FOUR LAWS

The whole thing stands on four laws

Break any one of them and the rest degrades into documentation — beautifully written, stopping nothing.

LAW 01

Fail closed on missing input

A missing file, a missing section, an empty data branch must go red. Defaulting to pass means the rule does not exist.

LAW 02

Every guard carries a reverse probe

Remove the protection and it must turn red, then restore byte-for-byte. A guard nobody has seen fail is not a guard.

LAW 03

One source of truth for cross-script rules

A single decision gets one implementation. Two regexes covering for each other only manufactures the appearance of passing.

LAW 04

Close the impact chain key by key

Missing keys must be named, not waved away with “I checked.” If coverage cannot be computed, it is not closed.

04 / THE PROOF

What it has caught

A fictional order system exports a CSV with the amount two decimal places off: 1234.56 comes out as 12.34.

The first instinct is to divide by 100 in the export module. That holds the symptom down. The third person who adds an export will get it wrong again.

So the cause was traced three levels up: the money unit had no single source of truth; it was passed around by naming convention. The fix therefore became “collapse it into one entry point, formatMoney(cents), and add a guard forbidding views to touch raw amounts.”

Then, before trusting that guard, prove it can actually go red:

reverse-probe
$ node reverse-probe.mjs --config probe.json
[reverse-probe] 基线通过 ✓

  ✓ 去掉 formatMoney 白名单：转红（exit=1）且复原一致
     首个红行：❌ 金额必须经 formatMoney()，不得裸用 amount
  ✓ 去掉金额判断：转红（exit=1）且复原一致
     首个红行：❌ 金额必须经 formatMoney()，不得裸用 amount

[reverse-probe] OK：2 个案例全部「变异转红 + 逐字节复原」

Still green after mutation means the gate is fake. It stops nothing; it is reassurance in script form.

verify-record — runs the record’s assertion table
$ node verify-record.mjs docs/change-records/2026-11-10-fix-money-export.md
[verify-record] docs/change-records/2026-11-10-fix-money-export.md
  ✓ #1 格式化函数唯一：1 行（期望 =1）
  ✓ #2 视图层不再裸用 amount：0 行（期望 =0）
  ✓ #3 导出模块已走格式化：2 行（期望 >=1）
  ✓ #4 移动端同步修复：1 行（期望 >=1）
  ✗ #5 报表模板同步修复：0 行（期望 >=1）

[verify-record] FAIL：1 项不合格

Assertion #5 went red: the report template was never updated. This is where it earns its keep — writing the record is how you discover what you missed.

The tools print in Chinese. Every line above is reproduced verbatim, so output you get locally will match exactly — not a translated approximation.

When an assertion goes red, change the code. Loosening the assertion so it goes green is smashing the instrument — after that, no number it prints means anything.
05 / THE TOOLS

Four tools you can run, not examples

Plain Node, no third-party dependencies. Every output above came out of them.

reverse-probe.mjs Mutation probe: break it → must go red → byte-identical restore, with hit counts checked
node plugins/ironlaw/skills/ironlaw-gate/scripts/reverse-probe.mjs --config probe.json
verify-record.mjs Executes the §2.5 assertion table of a change record, line by line, failing closed
node plugins/ironlaw/skills/ironlaw-record/scripts/verify-record.mjs docs/change-records/xxx.md
impact-scope.mjs Impact-chain scope keys: diff → keys → check each against assertions & reasons, naming every missed key (machine side of law 4)
node plugins/ironlaw/skills/ironlaw-record/scripts/impact-scope.mjs --base <ref> --record docs/change-records/xxx.md
ship-truth.mjs Four sources of truth: local, remote, live, artifact. Any mismatch means it is not shipped
node plugins/ironlaw/skills/ironlaw-ship/scripts/ship-truth.mjs --config ship.json
06 / INSTALL

Three ways in, pick one

Restart the WorkBuddy session after installing so skills are rescanned. A skill name is also a slash command.

OPTION 1 · RECOMMENDED

One command into WorkBuddy

Self-check the package, copy 6 skills, verify, print the commands you can use.

node scripts/install.mjs
OPTION 2

Mount as a plugin marketplace

The repo root carries a marketplace manifest; commands/ additionally enables slash commands with argument hints.

plugins/ironlaw/
OPTION 3

Skills only

No commands, just the six skill directories. The lightest path.

cp -r plugins/ironlaw/skills/* ~/.workbuddy/skills/

Useful flags: --dry-run show the plan · --list list package contents · --prune-legacy archive older loose skills (never deletes) · --target dir install at project level. Three ways to invoke: /ironlaw-change, or “use IronLaw on this bug”, or just describe the problem and let it route.
