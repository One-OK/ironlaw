把工程纪律
变成机器。

AI 和人都能很快写出「看起来对」的代码，但没人能证明它真的对。 IronLaw 不提升写代码的速度，它提升的是「这次改动可信」的可证明程度—— 把每一次判断都落成机器能查的东西：门禁、断言、真值核验。

01 / THE PROBLEM

「看起来对」和「可证明对」
差着一整套证据链

代码跑起来了、页面点得动、控制台没报错——这些都不构成证明。真正缺的是：改完以后，你凭什么说它对了？

看起来对常见状态

  • 本地跑通了，就当作改好了
  • 「其他地方我都检查过了」——没有清单
  • 测试是绿的，但没人验证过测试会不会红
  • 部署脚本说成功，线上还是旧版本
  • 同一个判定规则，在三个文件里各写了一遍

可证明对IronLaw 之后

  • 根因是一句话机制，不是复述症状
  • 影响链是机器算出的覆盖率，漏的键被点名
  • 守卫做过反向探针：改坏必须转红
  • 线上真值来自接口返回，不是部署脚本的自述
  • 判定规则只有一份实现，别的都是它的调用方

一句话：不要相信「我觉得改好了」。要么机器能查，要么就当没改。

02 / THE FOUR LAWS

整套东西立在四条铁律上

违反任何一条，其余部分就退化成「文档」——写着很好看，拦不住任何东西。

LAW 01

必填必须 fail-closed

缺文件、缺章节、空数据分支必须判红。默认放行等于条款不存在。

LAW 02

新守卫必须带反向探针

去掉保护必须转红，且能逐字节复原。不验证「改坏会红」的守卫，等于没有守卫。

LAW 03

跨脚本口径放单一真源

同一个判定只能有一份实现。禁止两份正则互相掩护——那只是在制造「都通过」的假象。

LAW 04

影响链用机器算的覆盖率逐键闭环

漏掉的键必须点名，不许用「都检查过了」结案。覆盖率算不出来的，就是还没闭环。

03 / THE PIPELINE

五段流程，按改动大小裁剪

不是每次都五段全跑。改一行文案只走第 2 段；动产品代码走 2–5 段；只有新项目才需要第 1 段。

1

bootstrap

scaffold

一次性铺设施：钩子、门禁、共享件、文档骨架。

2

change

discipline

开工六问 → 根因 → 影响链 → 修法，不是急着改代码。

3

gate

guards

把这次的判据钉成机器可查的守卫，并证明改坏会红。

4

record

evidence

七段档案 + 断言表 + 三段式提交信息，写档案就是查漏。

5

ship

truth

推送 → 出包 → 部署 → 四方真值核验 → 登记。

04 / THE PROOF

它抓错过什么

一个虚构的订单系统，导出的 CSV 里金额少了两位小数：1234.56 变成 12.34。

第一反应是在导出模块里补一个 ÷100。但那只是把症状按住——第三个人加导出时还会错。

于是往上追了三层，根因是：金额单位没有单一真源，靠命名口头传播。修法因此变成「收口成 formatMoney(cents) 唯一入口，并加守卫禁止视图层裸用 amount」。

然后守着这条判据，先证明守卫真的会红：

reverse-probe
$ node reverse-probe.mjs --config probe.json
[reverse-probe] 基线通过 ✓

  ✓ 去掉 formatMoney 白名单：转红（exit=1）且复原一致
     首个红行：❌ 金额必须经 formatMoney()，不得裸用 amount
  ✓ 去掉金额判断：转红（exit=1）且复原一致
     首个红行：❌ 金额必须经 formatMoney()，不得裸用 amount

[reverse-probe] OK：2 个案例全部「变异转红 + 逐字节复原」

变异后仍然全绿，说明这道门禁是假的——它拦不住任何东西，只是心理安慰。

verify-record — 执行档案里的断言表
$ node verify-record.mjs docs/change-records/2026-11-10-fix-money-export.md
[verify-record] docs/change-records/2026-11-10-fix-money-export.md
  ✓ #1 格式化函数唯一：1 行（期望 =1）
  ✓ #2 视图层不再裸用 amount：0 行（期望 =0）
  ✓ #3 导出模块已走格式化：2 行（期望 >=1）
  ✓ #4 移动端同步修复：1 行（期望 >=1）
  ✗ #5 报表模板同步修复：0 行（期望 >=1）

[verify-record] FAIL：1 项不合格
  - 断言 #5（报表模板同步修复）不成立：期望 >=1，实际 0 行

第 5 条红了，说明报表模板漏改。这是它最有用的地方：写档案的过程，就是发现自己漏改的过程。

ship-truth — 部署后核验四处真值
[ship-truth] 本地版本 1.4.2
  ✓ 版本一致：PASS — 1.4.2（3 处）
  ✓ 工作区干净：PASS — 无未提交改动
  ✓ 本地 = 远端：PASS — abc1234de
  ✓ 线上版本：PASS — 1.4.2
  ✓ 分发版本：PASS — 1.4.2
  ✓ 台账已登记：PASS — 最近 40 行含 1.4.2

[ship-truth] 6 通过 / 0 不一致 / 0 无法判定 / 0 跳过
断言红了就改代码。放宽断言让它变绿，等于把测量仪器砸了——从此以后每个数字都不可信。
05 / THE TOOLS

四个能直接跑的工具，不是示例

纯 Node，无第三方依赖。上面那些输出，就是它们跑出来的。

reverse-probe.mjs 反向变异探针：改坏 → 必须转红 → 逐字节复原，并校验命中数
node plugins/ironlaw/skills/ironlaw-gate/scripts/reverse-probe.mjs --config probe.json
verify-record.mjs 直接执行变更档案的 §2.5 断言表，逐条报告，不成立就 FAIL
node plugins/ironlaw/skills/ironlaw-record/scripts/verify-record.mjs docs/change-records/xxx.md
impact-scope.mjs 影响链范围键：diff → 范围键 → 逐键对照断言与理由，漏掉的键点名（铁律四的机器侧）
node plugins/ironlaw/skills/ironlaw-record/scripts/impact-scope.mjs --base <基线> --record docs/change-records/xxx.md
ship-truth.mjs 四方真值核验：本地 / 远端 / 线上 / 分发，四个不一致就不算发版
node plugins/ironlaw/skills/ironlaw-ship/scripts/ship-truth.mjs --config ship.json
06 / INSTALL

三种装法，选一种就够

装完重启 WorkBuddy 会话才会被扫描到。技能名本身就是斜杠命令。

方式一 · 推荐

一键装进 WorkBuddy

自动包自检 → 复制 6 个技能 → 装后复验 → 打印可用命令。

node scripts/install.mjs
方式二

作为插件市场挂载

仓库根含 marketplace 清单，commands/ 会额外启用斜杠命令与参数提示。

plugins/ironlaw/
方式三

只要技能文件

不装命令，只把六个技能目录复制过去，最轻。

cp -r plugins/ironlaw/skills/* ~/.workbuddy/skills/

常用参数：--dry-run 只看会做什么 · --list 列出包内容 · --prune-legacy 归档旧版散装技能（不删除） · --target dir 装到项目级。 调用就三句话：/ironlaw-change、或者说「用铁律修这个 bug」、或者直接描述问题让它自己路由。
