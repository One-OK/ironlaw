一个永远变绿的门禁，
成本比没有门禁更高。

没有门禁时，你至少知道自己是在凭感觉判断。有一道假门禁时，你以为有人在看—— 而且从此不再怀疑。这篇文章讲清楚：假绿是怎么产生的、怎样在五分钟内查出它， 以及为什么唯一的判据是「先证明它会红」。

00 / PREMISE门禁的价值，等于它变红的概率

大多数人评估门禁时会看它覆盖了什么。这个角度是错的。覆盖再全，只要它从不变红，它就没有产生过任何信息——它的唯一作用是把「没人检查」这件事伪装成「已经检查过了」。

换个角度看：一道门禁在代码被改坏时变红的概率，才是它的价值。100% 的守卫是真守卫；80% 的守卫是「大部分时候可信」；0% 的守卫是负资产——因为它消耗了本该用在别处的注意力，还附赠了一种虚假的安全感。

而 0% 的守卫非常容易写出来。下面七种写法，每一种都能让脚本稳定输出 PASS，其中大部分看起来很专业。

01 / FAKE GREEN七种让门禁永远变绿的方式

每一条都给出三件事：它会表现成什么样、机制是什么、以及怎么用机械手段查出来。第三条最重要——前两条只能让你警惕，第三条能让你抓住它。

01

零命中即通过

症状

门禁永远绿。把被保护的文件整个删掉，它还是绿的。

机制

守卫的判据是「不许出现 X」，实现成 grep -c X 得到 0 就放行。可是保护对象被删了，X 自然也不存在了——查找失败被当成了检查通过。这是最常见的一种，也是最难自己发现的，因为它的行为和正确实现几乎完全一致。

怎么查

在守卫里加一条前置断言：被扫描的文件数必须 ＞ 0，否则直接报错退出。这一条能挡住九成的零命中假绿。然后配合反向探针删掉被保护文件，确认它转红。

零命中的两种形态
# 假绿：没有匹配 = 通过
n=$(grep -rc "裸用 amount" src | wc -l)
[ "$n" -eq 0 ] || fail

# 真守卫：先证明扫到了东西，再判内容
files=$(find src -name '*.ts' | wc -l)
[ "$files" -gt 0 ] || die "没扫到任何文件，判红"
grep -rq "裸用 amount" src && fail
02

空数据分支返回真

症状

本地跑全绿，一到有真实数据的环境就出错。或者数据被清空后，门禁反而「更健康」了。

机制

校验逻辑写在循环体里，循环没进去就直接走到结尾的 return true。空数组、空表、空目录都是触发器——而空数据恰恰是最常见的新环境状态。

怎么查

为每个校验补一个空输入用例，并明确它的期望：要么判红，要么显式记为「无法判定」。绝不允许它静默算作通过。判据是「有数据时该红能红，没数据时不许算过」这两句同时成立。

03

异常降级成警告

症状

日志里一路 warn 甚至 error，退出码却是 0。翻日志的人越来越少，因为「反正每天都这样」。

机制

try { … } catch (e) { console.warn(e) }。捕获本身没错，错在捕获之后没有改变结论。守卫遇到读不到文件、解析失败、接口超时，都会走进这条分支——而这些都是「检查没做完」，不是「检查通过」。

怎么查

把「警告数必须为 0」做成硬指标，或者让 catch 分支显式非零退出。中间态最危险：只有两种允许的结局——查完了通过、查不下去判红。

三档结论，不要合并
// 假绿：异常被吞，退出码由最后一步决定
try { check(f) } catch (e) { warn(e) }   // 继续往下跑 → exit 0

// 真守卫：三种结局各自可辨
assert(cond, msg)      // 判据不成立 → 红，进程非零退出
soft(msg)              // 样本缺失 → 记「无法判定」，不计入通过数
skip(msg)              // 前置不满足 → 记「跳过」，超过阈值即判红
04

跳过被算作通过

症状

报告写着「6 个用例全部通过」，实际跑了 2 个，4 个 skip。没人去数。

机制

跳过与通过共用同一个计数变量。更隐蔽的版本是同一个条件既判红又 skip——两条分支各自看起来都对，合起来就永远有一条能接住失败，于是永不判红。

怎么查

把结论拆成四个独立数字：通过 / 不一致 / 无法判定 / 跳过，并给 skip 设阈值。同时立一条规矩：同一个条件不得既判红又 skip——一个条件只能有一个归属。

05

用存在性代替内容

症状

文件在、导出在、函数名在，但函数体被清空成 return null，门禁依旧绿。

机制

existsSync(path) 或 content.includes('formatMoney')。前者只证明路径存在，后者只证明字符串出现过——注释里出现也算。这两种判据的共同问题是它们描述的是文本，不是行为。

怎么查

把判据从「有这个名字」换成「有多少个调用点」「从这里到那里有没有通路」。最直接的验证仍然是变异：把函数体清空，看它红不红。

06

两份实现互相掩护

症状

两份规则看起来都对，删掉任何一份，检查结果仍然是绿。

机制

同一个判定被写了两遍：一处检查正则 A，另一处检查正则 B，各自只覆盖一半。你以为「双保险」，实际是任何一份失效都会被另一份的偶然覆盖掩盖。最坏的情况是两份都不完整，却因为互相兜底而从未同时暴露。

怎么查

把口径收进单一真源（一个 lib、一份配置、一张清单），两份检查都引用它。收口之后再做一次反向探针：只改动真源，两处必须同时转红。如果只有一处红，说明还有一份没接上。

判断标准：「把这条规则从代码里删掉，需要改几个地方才能删干净？」答案大于 1，就是有两份真源。这个问句比任何架构图都准。
07

检查的是过期产物

症状

源码改了，门禁查的是上一次的构建结果。构建失败时，旧产物还在原地，门禁对着旧文件一路绿。

机制

产物目录没清空就重新构建；构建失败但脚本继续往下走；或者门禁直接读 dist/ 而不验证它比源码新。

怎么查

构建前先删产物目录，让「产物缺失」成为一个必然出现的红灯，而不是被旧文件悄悄兜住。再加一条时间断言：产物的修改时间必须晚于所有源文件——这条能一次抓住「构建其实没跑」。

这七种有同一个内核：把「我没检查出来」编码成了「没有问题」。它们的差别只在措辞——找不到、没数据、出异常、跳过了、名字在、别人查过、文件是旧的。识别假绿时不必记这七条，只问一句：这次绿，是因为我查过了，还是因为我没有查到？

02 / FAKE RED假红：比假绿更慢的毒药

假绿让人误判一次。假红会让人永久失去判据——因为它的最终产物不是一次错误的通过，而是一个学会忽略告警的团队。一旦「红了先重跑」「红了先看看是不是环境问题」成为习惯，真的红灯也就没人看了。

三种最常见的假红：

  • 时序与网络抖动。接口偶发 502、端口还没起来、DNS 慢了一拍。判据本身没问题，环境没准备好。处理方式不是加宽判据，而是把「环境未就绪」和「结论不成立」分成两类结论：前者记「无法判定」，后者才判红。
  • 判据钉在文案上。expect(text).toContain('导出成功')。改一个字就红，而产品行为完全正确。判据应当钉结构（哪个元素、哪个字段、哪个状态码），而不是钉人类可读的字符串——文案是会变的，结构才是契约。
  • 超时设得太紧。大任务被砍掉，脚本报失败。这种情况最容易被误判成真失败，从而引发「这检查没用」的结论。被超时杀掉的进程必须区别于判定失败，单独给一个状态（比如退出码 3 = 疑似设施问题），并且在输出里明确写出来——否则它会被当成红。
一个可操作的分界：任何一次红灯，先问「换台机器、把条件原样重跑一次，还会红吗」。会 → 真问题。不会 → 先修环境或修判据，别急着改代码；但也别把它当成通过，记「无法判定」。

03 / THE PROBE唯一可信的判据：先证明它会红

以上十种毛病的共同点是：光看代码看不出来。写得再像真的守卫，也可能是假的。所以唯一可靠的验证方式只剩一个动作——

把保护改坏，看它红不红。红完再把文件逐字节复原。

这叫反向变异探针。它有三条必须同时成立的要求，少一条就会退化成新的假绿：

  1. 变异必须真的改坏东西。改注释、改空白不算。要改的是保护点本身：删掉白名单、去掉判断、清空函数体。
  2. 转红之后必须逐字节复原。用 md5 或 sha256 校验，不是靠 git checkout 的「应该没事了」。探针跑完代码和跑之前必须完全一致，否则探针本身是破坏性的。
  3. 变异必须命中预期次数。如果替换了 0 次，那不是「守卫有效」，是探针配置错了——它什么都没改，却因为门禁恰好是绿的而报告成功。这条最容易漏，也最讽刺：一个用来查假绿的工具，自己假绿了。

所以探针的退出码必须是三态，而不是成败两态：

探针的三态
0  变异后转红，且复原校验一致        → 守卫是真的
1  变异后仍然全绿                  → 守卫是假的（假守护）
2  配置错误 / 命中数不符 / 复原失败  → 探针自己坏了，结论作废

把 1 和 2 合并成一个「失败」是常见错误。它们的处置完全不同：1 要改守卫逻辑，2 要改探针配置。混在一起，你会拿着一个配置错误去重写一份本来正确的守卫。

真实跑起来是这样：

reverse-probe — 变异转红 + 逐字节复原
$ node plugins/ironlaw/skills/ironlaw-gate/scripts/reverse-probe.mjs --config probe.json
[reverse-probe] 基线通过 ✓

  ✓ 去掉 formatMoney 白名单：转红（exit=1）且复原一致
     首个红行：❌ 金额必须经 formatMoney()，不得裸用 amount
  ✓ 去掉金额判断：转红（exit=1）且复原一致
     首个红行：❌ 金额必须经 formatMoney()，不得裸用 amount

[reverse-probe] OK：2 个案例全部「变异转红 + 逐字节复原」

注意第一行的「基线通过」。探针必须先确认没变异时门禁是绿的，否则后面「变异后转红」毫无意义——一道本来就红的门禁，任何变异都能让它红，这种验证不能说明任何事。

顺序不能反：先绿 → 再变异 → 必须红 → 复原后必须又绿。四步缺一步，这个验证就不成立。跳过最后一步的人最多——他们证明了自己能把门禁弄红，却不知道代码有没有被留在改坏的状态。

04 / CHECKLIST十问清单

下次写守卫、或者接手一套已有门禁时，逐条问。全部答案为「是」才算通过——注意这里同样是 fail-closed：答不上来就是没有。

01

删掉被保护的文件，它会红吗？——查零命中假绿。

02

数据为空时，它算通过还是算无法判定？——查空数据分支。

03

读不到文件、接口超时，退出码是什么？——查异常降级。

04

报告里的「通过数」，包含跳过的吗？——查 skip 混算。

05

判据里有几个数据库表名、文案词、人类可读的字符串？——有就是钉错了层。

06

把规则从代码里删干净，要改几处？——大于 1 便有两份真源。

07

它检查的是源码还是产物？产物比源码新吗？——查过期产物。

08

它最近一次变红是什么时候？为什么红？——从来没红过，要么项目完美，要么它没用。

09

它有对应的变异探针吗？探针区分「守卫是假的」和「探针坏了」吗？

10

红灯出现时，团队的第一反应是查原因，还是先重跑？——这决定了整套门禁还剩多少可信度。

最后一条最要紧。前九条是工程问题，可以靠改代码解决。第十条是文化问题：一串红灯如果让人的第一反应是「再跑一次」，那这套门禁的可信度已经归零了，而修复它需要的不是新工具，是把假红彻底清掉——一次也不要留。

这套东西的用法可以压缩成一句话：断言红了就改代码，不要改断言。放宽断言让它变绿，等于把测量仪器砸了——从此以后每个数字都不可信，包括那些看起来对的。
